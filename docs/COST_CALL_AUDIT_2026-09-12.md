**文本调用多：有正常工具循环，也有仍需优化的重复上下文**

已结算文本记录共 **93 次，$1.6963641**。其中 SDK 完成响应 85 次，模型分布为 Terra 68、Sol 14、Luna 3；它们与逐笔 SDK 账目数量一致。剩余 8 次为 SDK 之外的轻量路由分类、标题等调用。因此“一个用户消息出现多笔文本扣费”并不直接等于重复扣账：工具调用前后的决策、研究、设计、审查都可能需要一次模型响应。

但有三个具体问题值得继续处理：

1. **恢复时重复追加阶段输入。** `runStage` 恢复 `sessions[key]` 后，仍把当前阶段的完整 `message` 再传给 `runner.run`。在 `afd5049c` 的 design 检查点中，完全相同的 36,682 字符用户输入实际出现了两次。其他恢复任务虽然因附加恢复说明而不是逐字相同，也再次包含同一用户目标。禁用超时自动重跑已减少触发机会，但恢复路径本身仍应按阶段输入去重。
2. **审查输入过大且有多份重叠内容。** 当前审查输入同时包含用户上下文、研究简报、设计答复、工具输出、交付验收、最新节点内容和图片；恢复后还会附加已完成工具摘要。六张图任务的一次最终审查输入为 45,558 个计费单位、费用 $0.1101327。四张图任务一次最终审查输入为 44,453、费用 $0.1077542；这轮图像费仅 $0.184126。应保留真实视觉验收，同时删除重复 JSON、历史工具全文和无关阶段内容。
3. **审查开始得过早，并在中断后再次执行。** 四张图任务在仅有三张图时进入第一次审查，再补第 4 张、再次审查，中断后又恢复最终审查。三次审查启动中，两个完成响应可对到账单，合计 $0.1630349。还确认了一个具体解析缺陷：图片关键词识别包含“图片”“图像”“效果图”，却遗漏“4张图”“共6张图”中的“图”。这两条真实需求保存的 `deliveryContract` 均为空，用当前 `delivery_contract()` 纯函数重现也返回空数组；对照“设计4张图片”可以得到 count=4。因此本地检查没有提前发现图片数量不足，留给付费审查才发现。应先修复交付数量识别，数量齐备后再执行内容审查；只有产物内容变化才重新审查对应部分。

**费用控制和审计还缺什么**

当前数据库没有自定义 `model_settings`，因此使用默认配置，`taskBudgetPoints=None`：没有开启单轮积分预算。生成工具接受 Agent 决定的视频时长；本轮 10 秒视频就是具体例子。工具参数、模型选择和单次响应有各自限制，但没有对用户一次需求的总支出形成统一约束。

建议按以下顺序优化：

1. 修复恢复消息去重，把交付数量检查放在模型审查之前；按节点内容指纹复用已完成审查。
2. 按阶段压缩上下文，审查只读本轮产物与直接参考；跨阶段共享已取得来源，避免设计阶段重新做同一批研究。
3. 在现有积分预算能力上增加明确的默认费用策略，并展示视频时长、画质与预计积分；用户未指定时采用明确的产品默认值，而非让 Agent 无提示地延长。
4. 给每笔模型请求记录供应商 response/generation ID、阶段、重试父请求、开始/终止状态。现在文本账目只有本地 attempt ID 与序号，无法完整对照供应商 Activity；中断响应未返回用量时，也可能缺少待核对记录。

本报告能确认本地账目和截图汇总基本一致、媒体生成数量一致、历史 Agent 重试存在。对于被中断且供应商未返回用量的请求，不能仅凭本地日志断定一定没有收费，也不能反过来认定一定重复收费。
