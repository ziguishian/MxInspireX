# 生成前的设计范围规划

品牌视觉、品牌全案、整套礼盒/包装和完整设计方案先确定本轮交付清单，再调用创作工具。范围框架是产品内置的检查提示，不是强制行业标准，也不代表用户已经购买或要求其中所有内容。

- 品牌任务检查定位、核心识别、实际应用、使用规范与交付。
- 全案任务检查目标与条件、整体概念、专业设计系统、关键表达、落地与交付边界。
- 每项必须按本轮需求明确为纳入、暂缓或不适用；保留用户已有要求，避免擅自扩大工作范围。
- 解释性问题、明确的局部修改不重新启动全案。

主 Agent 使用 `design_plan` 读取框架或保存公开计划，包含目标、保留项、交付物、具体验收条件、范围取舍、关键未决问题和研究需求。计划原子保存到当前任务的 `input_json.designPlan`，重复保存同一计划不增加版本。不创建额外的计划画布节点，也不另起付费“思考 Agent”。规划仍使用现有 Agent 的正常模型调用，不能理解为完全没有模型费用。

通用的设计范围先根据框架、上下文和专业知识判断；缺少具体行业、竞品、事实或案例依据时再定向检索已有资料，允许联网时使用现有 `web_search` / `web_read`。已有搜索预算和故障停止规则继续生效。不会为了每个设计任务强制搜索，也不会声称没有实际查看过的图片已被分析。

只有影响整个方向的关键未决问题才将计划标为待补充，并转入逐题提问卡片。尺寸等局部依赖写入相应交付项的 `blockingFields`，其他项继续执行。用户已说明“暂未提供官方色值”等内容也视为已回答，不重复提问；概念配色仍须说明尚未经官方确认。

卡片悬浮在输入框上方，脱离普通文档流，不压缩聊天区域；答案和跳过状态汇总后一次提交。提交包含原问题 ID、位置、答案与跳过状态，后端从真实提问任务校验，不依赖模型从长段补充文字中重新猜答案。补充任务继承原始引用、已确认决策和范围框架，结合回答重新确定计划。

`designState` 按任务保存目标和有来源的决策快照。确认信息、临时假设、未知和跳过分开保存。`design_state` 工具确认事实时必须逐字引用项目内的用户原文；旧来源或模型假设不能覆盖较新的确认信息。普通续接沿用当前目标，新整套需求或明确“新项目”重新建立范围。用户说“好的”“继续”“按计划生成全部图像”时，沿用已就绪计划；最后一种只推进其中图像项。新增修改要求进入计划调整，不能把旧版本的审查当成新要求已完成。

已识别的品牌/全案任务若没有就绪计划，创作工具返回 `planning_required`，不发出生成请求或占用收费回执。Worker 不缓存这个阻止结果，保存就绪计划后可以继续同一次生成调用。计划通过上下文过滤接口持续提供给执行和审查阶段；完整内容可用 `design_plan` 只读获取。

交付项有稳定 ID，创建工具用 `deliverable_ids` 将实际节点绑定到清单。只有一项同类交付时可自动关联；多项时必须明确指定。用户明确要求的文件数量必须拆成对应交付项，接受计划后的继续执行不能删项或降低验收条件。一份手册或综合图可以覆盖多项，但每项必须有独立内容核查；一个节点或同类文件存在不等于全部完成。

交付检查发现尚未生成的项目时，主 Agent 最多进入一次补齐阶段，按原清单继续创作，沿用正常预算和收费回执。已有成功产物直接复用；需要修改时明确指向原节点。缺资料的项目保留为阻塞状态。本地技术检查或模型审查未通过时直接标记 `needs_review`，不自动修改文本、网页或图片；用户明确发起修复后才进入新的修改任务。

效果图使用图像生成工具；生产 Agent 的 SVG 生成全局禁用。需要精确文字时按用途使用 HTML/CSS，需要实体或参数化结构时使用 CAD；要求矢量或模型的交付项不能用栅格效果图冒充。

进度区显示每项的待交付、生成中、等待资料、已生成待审查、已通过和待修正状态，并可展开本轮确认信息与假设。整轮执行结束仍有缺项时，界面和答复会保留待处理项。仅在要求、决策、验收条件与全部产物版本一致且上一轮整体审查通过时，才复用审查结果。

验证：`services/api/tests/test_design_planning.py`、`services/api/tests/test_design_execution.py`、SDK 模拟传输测试、`npm run test:clarification`。覆盖杭州礼盒原始需求、跨轮澄清、续接、两图分别交付、局部资料阻塞、缺项补齐、补齐时新增提问、审查复用及失效、SVG 禁用和窄窗口进度。测试使用临时项目和模拟模型，不调用真实付费服务。
