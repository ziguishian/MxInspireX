# 对话记忆与图像质量

当前一个项目对应一个主聊天，记忆与 SDK 主会话共用 `project:<projectId>` 标识，SQLite 位于当前工作区。打开新聊天会创建独立项目，不会继承其他聊天的记忆。工作区切换后使用对应数据库。

## 执行路径

1. `TaskRuntime` 从服务端消息与附件建立真实任务；客户端不能传入记忆状态。旧聊天按需导入图片身份与来源，正文事实由主 Agent 阅读原始历史后提取。
2. `ConversationMemoryService` 提供有效信息目录、主题/任务范围过滤及检索；SDK 主 Agent 调用 `conversation_memory_read` / `conversation_memory_update` 分析、修正和选择本轮信息。主题只收窄自动召回，Agent 可以显式选用旧主题中仍适用的记录，记录本身的原主题和范围保持不变。
3. 保存采用乐观版本检查与操作回执。正文版本不可变；每轮选择、引用快照和真实进度写入任务状态。一次性约束与持续约束使用独立 key。
4. `prepareModelInput` 为选中的完整记忆、必要原图预览、活跃 Skill 保留独立空间。下一次模型调用立即使用更新。旧轮图片按需补读，原始 Session 不改写。请求清单记录实际送入的记忆 ID、版本与引用。
5. 开始制作前检查本轮是否分析完毕。图像单项、批量及节点编辑检查最终 source 参数与交付项引用快照一致。引用快照使用设计计划中的稳定交付项 ID；只有一个当前交付项时，服务端会把模型写出的单个临时别名归一为该 ID，多项歧义则返回可修正错误。任何一项批量引用错误都会在该批开始前返回可修正错误。

   显式 `references=[]` 表示本轮不向生成模型提供参考图，保存为 `deliverableId=*` 的空引用快照。本次提交 `selected_ids` 但省略 `references` 时建立 `bindingPolicy=candidates` 的候选快照，各交付项可以使用其子集；显式 references 仍为严格绑定。只更新记忆内容时保持原绑定策略；旧快照没有 bindingPolicy，继续按严格绑定处理，不迁移历史任务。旧任务若已完成分析、未选择任何图片且没有引用快照，可继续无参考生成。预检仅保存独立的版本校验记录，不创建资产、画布节点或收费回执。
6. Agent 先实际看图并反推视觉描述，再融合本项需求。纯借鉴参考只注入文字；需要保真或修改的参考由图像供应商读取原始资产文件，模型阅读可以使用缩略图。实际来源、融合方案、供应商实际图片输入、模型、质量参数、尺寸与节点回执保存到资产和任务进度。

## 图像请求统一解析

`image_request_resolution.py` 供单图、批量预检和 `image_edit` 共用。它按明确的工具来源、当前画布绑定和计划输入解析真实资产，合并来源依据，区分来源节点与输出节点。`image_intent.py` 在同一预检中依据用户原文、逐图绑定和视觉分析推导 `edit | reference | ambiguous`，但不替 Agent 编造视觉分析。智能参考库候选不自动注入请求；Worker 不再替每一项加入全部已选参考。

图像 `output_mode` 可省略，系统统一新建并保留原图。输入框随本轮附带的普通图片是参考候选，不是待覆盖节点；同轮未被用户明确要求沿用排版/构图时，即使 Agent 计划误写为 `layout` 也归一为 `reference`。已接受计划、明确版式要求和套系母版继续保留严格的 `layout + preserve` 校验。旧调用中的已有图像 `canvas_node_id` 转为来源；当前画布输入的空白图像节点才允许填充。冲突目标、跨项目来源和非图像节点返回明确错误，非图像编辑不改变。

输入框附件、资产引用和画布连线都不提供逐图用途选择；客户端的新草稿、队列、重发和画布任务不会提交或沿用旧 `referenceMode/referenceModes` 覆盖值。图片用途统一根据用户原文、图片绑定关系和视觉分析智能判断。明确“不修改、只参考”优先；具体图片或图中对象发生增删、替换、改色、换背景以及时间、环境或状态变化时为 `edit`；“生成、制作、做一张”不改变这一判断。多图请求只有资产提及、文件名或“图1/图2”等能够唯一绑定某张图片时才对该图做高置信度强校验；同一分句同时列出多张图，或只说“参考图/这张图”而无法区分对象时保持 `ambiguous`，由 Agent 的逐图分析决定。“这两张图都/所有图片”等明确整体指令仍应用到全部图片。只有不同判断会影响保留范围时才澄清。历史任务中的旧字段只用于兼容读取，重新提交时会移除。

高置信度判断与 `reference_analysis.mode` 冲突时返回 `reference_mode_mismatch`，错误包含资产 ID、预期/实际模式、判断来源和原文证据。该检查发生在 Provider、加载节点和计费回执之前；Worker 获得一次自动修正机会，再次冲突便停止并展示可操作提示。最终引用快照在 `resolution.referenceIntents` 保存判断来源、证据、实际模式和是否发送像素，在 `providerInputAssetIds` 保存实际原图输入。

`generation_reference_check` 保留 `snapshots` / `imageRequests`，新增 `resolvedOperations`，包含操作索引、来源及用途、资产哈希、节点内容版本、输出位置、交付绑定和待就绪依赖。错误携带 `errors` 的操作索引、字段及相关资产/节点。严格引用方案要求多图但 Agent 仅漏传部分 ID、同时已经为方案内每张图提交完整逐图分析时，预检按已保存方案补齐 ID，并在 `memoryReconciliation` 记录提交值与最终值，不额外消耗一次模型修正；如果包含方案外图片或缺少任一逐图分析，仍返回精确的 `expectedAssetIds`、`actualAssetIds`、`missingAssetIds` 和 `unexpectedAssetIds`。缺少分析不会通过删图或编造分析放行。整批校验成功后，在已有 `conversation_reference_snapshots` 表保存 `image-preflight:` 前缀的记录；无新增表。执行重用同一解析器，比对版本；变化返回 `reference_changed`，需要重新预检。移动节点位置不改变内容版本。

同批次未来产物只按依赖 ID 登记；已有输入继续校验，未来输入执行时解析。实际看图要求仍在后续生成前检查。回执指纹使用收到的原始参数，内部归一化及预检摘要不进入指纹；已完成回执先复用，未知结果继续阻止重发。预检不调用图像模型、不产生加载节点。

验证入口：`test_image_request_resolution.py` 包含原始遗漏输出模式案例、真实 SDK 单图/批量模拟、候选选择、版本变化、重启和防重复收费；依赖调度与非图像行为继续由已有测试覆盖。

## 图像参考反推与需求融合

`image_reference_design.mjs` 提供主 Agent 的统一方法和 `reference_analysis` schema；`image_reference_design.py` 负责校验、必要的图像输入编号/保留约束和实际图片输入选择。主 Agent 将实际采用的特征提炼到最终 `prompt`，不传推理、流程和交付说明；后端不再整段拼接参考分析、设计计划或前置文档。它们不额外调用视觉模型，由已经能看到图片的主 Agent 分析；只能反推可见视觉特征，不能声称恢复原作者真实提示词。参考库标签、OCR 和旧生成提示词不能替代实际看图。

每个生成项提交 `reference_analysis.images`（逐图 `asset_id`、`visual_prompt`、`mode`、`use`、`avoid`、`preserve`）和 `synthesis`（本项目标、内容、载体与参考的融合方式）。`source_asset_ids` 保留全部语义参考，与记忆引用方案一致；以下用途只控制实际图像模型输入，不删除来源关系：

- `inspiration`：提取配色、构图、材质或内容启发，文字融合后重新设计；不向图像模型发送这张参考的像素。
- `identity`：用户要求保持 Logo、IP、产品或版式身份，必须写 `preserve`，向图像模型发送原图，并明确对应的实际输入序号。
- `layout`：用户画板或草图的结构布局参考，发送原图约束主体位置、相对比例和留白，不把笔触、辅助线与临时配色复制成成品风格。`metadata.source=canvas-drawing` 的图像在预检和实际生成中统一按布局参考处理。
- `edit`：用户明确要求修改这张原图，必须写 `preserve` 和修改范围，发送原图，在新节点保存结果。视觉分析只辅助理解，不得把局部改图扩写成重新设计；默认保留未涉及的主体、文字、Logo、构图和装饰。分析由 Agent 完成，不要求用户另写反推提示词。遮罩重绘提交分析时，原图必须为 `edit`，单项执行和批量预检均校验；本地裁剪、缩放、格式转换不要求这套分析。

启用对话记忆协议的 Agent 图像生成必须覆盖所有实际参考；缺分析、遗漏图片或缺保留项会返回 `reference_analysis_required`，没有收费请求或加载节点。批量预检对当前可用参考逐项校验；未来图片仍在实际执行时校验，Agent 应先生成并查看前置图片再准备后续分析。一般连续校验失败沿用有限修正后停止的机制；`reference_mode_mismatch` 只允许修正一次。历史成功和未知收费回执仍优先处理，不能通过补写分析重发未知请求。无参考生成、未启用记忆协议的旧调用和直接 API 保持兼容；直接调用者可显式提供同样的分析。

资产 `referenceSnapshot.analysis` 保存反推与融合内容，`sourceAssetIds` 保存全部来源，`providerInputAssetIds` 单独记录实际发送的图片。验收按用途检查：借鉴检查设计融合，保真检查身份，编辑检查修改范围。相关验证见 `test_image_reference_design.py`、`test_memory_sdk.py`。
7. 验收读取原始依据及生成结果，缓存关联引用快照。重启恢复使用原任务快照和已完成回执。研究、审查、修复角色只能读取本轮快照。

生成图默认是 `artifact`。用户通过附件/资产引用明确采用后可更新用途；已确认计划中的辅助母版依赖也可通过真实计划 ID、交付项与资产绑定证明采用关系。历史排序不会自动把生成图升级为原 Logo。

记忆上下文的 `sourceEvidence` 分别提供服务器保存的用户原文与真实附件关联。`source.quote` 逐字引用原文，附件标签用于定位图片。引文校验失败时，回执返回具体 key、字段、原文依据和当前 revision；整次修改回滚，已有选择保留。模型请求保留失败参数供修正，成功回执才摘要化。原始执行记录区分“工具失败”和“工具完成”，引用不匹配也按失败显示。连续四次记忆写入被拒绝，或同一生成工具连续三次一般参数校验失败时，以工具错误停止；`reference_mismatch` 与 `reference_mode_mismatch` 只允许一次模型修正，再次不一致即停止。所有这些路径都保留证据，不进入模型升级或付费重试。

## 图像质量

- 图像策略同时决定媒体模型档位、Provider 质量和分辨率。常规设计默认 `standard / medium / 2K`；方向探索与概念草图使用 `draft / low / 1K`；正式交付和需要保真的引用编辑使用 `final / high / 2K`；印刷、大屏、喷绘等生产用途使用 `final / high / 4K`。
- 用户明确指定模型、像素尺寸、`1K/2K/4K` 或质量时优先。明确要求“超高质量 / xhigh”映射为 `quality=xhigh + 4K`；“最好、最高质量、质量拉满”等映射为 GPT Image 2.5 的 `quality=max + 4K`。同时指定具体尺寸或分辨率时，以具体尺寸要求为准。手动模型不被自动路由替换。
- 自动模型选择使用 `draft / standard / final` 三个媒体槽位；默认分别为 Flare / Sunburst / Sunburst。探索链为 Flare → Sunburst → GPT Image 2 → Seedream，常规、最终与参考图精修链为 Sunburst → Flare → GPT Image 2 → Seedream。预检在 `imageRequests[]` 保存 `routeMode`、`primaryModel`、`candidateModels`，执行时仍重新核对最新目录与引用版本。
- 成功资产、画布节点和工具回执保存 `imageRoute`；其中列出候选状态、实际模型、是否降级和参数调整。`imageQuality.model` 始终是成功候选。会话进度只在真实发生降级时提示“首选不可用，已使用 …”。
- 早期 GPT Image 的 final 使用 `high`，DALL-E 3 的高质量使用 `hd`。适配器已支持的参考保真参数设为 `high`；GPT Image 2 系列省略不可调的 `input_fidelity`。
- 未声明可调质量的接口不添加猜测参数，记录 `unsupported`。供应商拒绝参数时报告配置错误，不静默降档重试。
- “测试”“先看效果”本身仍按常规 `medium / 2K`，不会仅因速度词降成草稿。明确的概念草图、构图测试、情绪板和方向探索才使用 `low / 1K`；引用已有草稿本身不构成降低质量要求。
- 尺寸按用途/比例选择，明确 size 优先。图像工具、画布生成、批量、直接接口、重新生成和蒙版编辑共用策略。
- GPT Image 2.5 在发送前校验宽高 16 倍数、单边 3840 上限、长短边比 3:1 上限、总像素 655360–8294400。显式像素 size 清除继承的比例/分辨率提示，实际参数写回资产记录。OpenRouter 的比例参数使用其接口支持的集合；不支持的比例先返回可修正错误，尚未创建加载节点或调用模型。
- 参数依据：[OpenAI 图像文档](https://developers.openai.com/api/docs/guides/image-generation)、[OpenRouter 模型端点能力](https://openrouter.ai/api/v1/images/models/openai/gpt-image-2.5-sunburst/endpoints)（2026-09-15 确认 quality 包含 max；aspect_ratio 不含 4:5）。
- 产物继续使用 PNG/JPEG/WebP。SVG 全局禁用。

## 图像生成进度

准备参数、读取参考资料、校验凭据及预算时，画布不新增图像占位。内置图像适配器在请求组装完成、即将发送模型请求时调用 `image_request_started()`；该调用通过独立的 ContextVar 通知本次工具创建加载节点，不向供应商传入内部回调参数。图像返回后替换同一节点。自定义适配器可声明 `reports_image_request_start=True` 并遵循同一通知契约；未声明者按其 `generate()` 调用边界保守处理。

图像调整使用原图资产作为输入，并为加载状态和最终结果创建新节点，原图节点不进入生成状态也不会被替换；系统交付修复也遵循这一规则。只有不含图像的空白待生成节点可以直接填充。服务端明确拒绝请求时，自动创建的空占位被移除；超时或响应丢失仍保留未确认回执，防止重复付费调用。执行列表保留中间尝试但使用普通进度样式；最终未解决的任务只显示一条失败总结，账户、预算等需要用户处理的原因保持可见。

## 测试方式

自动测试全部使用临时工作区和模拟上游。`test_memory_sdk.py` 运行真实已安装 SDK，覆盖 Responses、Chat Completions、引用错误整批阻止、中断恢复及避免重复生成，也覆盖误把附件标签当引文后修正出图，以及重复校验失败时停止且图像调用数为零；`test_image_quality.py` 检查实际 JSON/multipart 请求参数。

```sh
services/api/.venv/bin/python -m pytest services/api/tests -q
npm test
npm run typecheck
npm run build
```

人工测试可在一个聊天中上传 Logo，然后依次发送：

1. “这是博览会的原 Logo，标准色用蓝色，帮我做一组活动物料。”
2. “再做六款胸针。”
3. “做水杯和帆布包，用原 Logo 延展。”
4. “这次水杯用绿色。”
5. “接着做一张海报。”

展开“本轮使用的对话信息”核对用途、范围、来源、版本与实际质量参数。第 3 步应引用原 Logo；第 4 步的临时绿色应仅影响对应任务。重新打开同一聊天继续后仍能提取信息；新聊天应为空。

这些自动测试验证执行和数据链路。设计质量、文字一致性与图形保真仍需用用户选定的真实图像模型进行视觉验收。
